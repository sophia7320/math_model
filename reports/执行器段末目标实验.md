# 执行器"段末硬目标"机制对照实验（小样本）

> 日期：2026-09-13（同日二次修订：末段漏洞修复后重跑）  
> 数据：附件 2/3 实测（小样本，不做全年大仿真）  
> 引擎：统一结构（2 日滚动 + EWMA h=5 预测 + κ/m + 40 情景联合残差对冲）  
> 复现：`uv run python -m solve.experiments.exec_policy_probe`（输出 `code/outputs/exec_policy_probe.csv`）

## 1. 问题定位

原逐槽因果执行器（`q2.exec_segment_causal`）要求 SOC 在每个决策段的末端
（6:00/12:00/18:00/24:00）跟踪规划轨迹（"可达性投影"）。实测该机制会：

- 在段末为达成高目标而**被迫充电**（电量不够高时），充电负荷叠加缺口 →
  **紧急购电（5 倍价）充能**；
- 在目标偏低时**扣留放电**，让本可由储能覆盖的缺口走紧急购电。

另一并行分析（基于旧引擎 result3.xlsx 的逐槽分解）显示：紧急购电的
四个小时尖峰（5:00 / 11:00 / 17:00 / 23:00）合计约占全年紧急量的 69%，
即该机制的产物。

**2026-09-13 二次排查发现**：`simulate_day_rt_hedge` 的最后一段
（18:00–24:00）直接调用 `exec_segment_causal(..., E_target[143])`，
绕过了 `run_exec` 的策略开关——首轮实验中的 `free` 实际是
"中段自由 + 末段跟踪日末目标"（= 修复后的 `dayend` 行为），
`free` 与 `dayend` 同值是代码结构所致，而非报告中"日末目标不 binding"。
修复后（末段改走 `run_exec(..., last=True)`），两者才真正区分。

## 2. 实验设计

在统一结构下，用两个小样本对比三种执行策略（计划层完全相同，仅执行层不同）：

| 策略 | 含义 |
|---|---|
| `target` | 段末目标硬跟踪（旧口径，四段全跟踪） |
| `dayend` | 仅当日最后一段跟踪日末目标，中间段自由 |
| `free` | 无任何段末目标（含末段），仅受容量/功率约束（现行统一口径） |

样本：夏季应力（2025-06-01 ~ 07-30，60 天）、秋季应力（2025-10-16 ~ 12-01，47 天）。

## 4. 结论

1. **段末硬目标是纯损失，且分两段**：
   - 中段目标（`target` → `dayend`）：夏季 +40.3 万（12.2%）、秋季 +8.4 万（4.3%），
     来自 0-6 / 12-18 窗口的紧急购电尖峰（接近清零）；
   - 末段目标（`dayend` → `free`）：夏季再 +4.6 万（1.6%）、秋季再 +0.5 万（0.3%），
     主要来自 18-24 窗口紧急（夏季 4.9 → 2.9 万）与计划电量微降。
   - 合计 `free` 相对 `target`：夏季 −44.9 万（−13.6%）、秋季 −8.9 万（−4.5%）。
2. **储能仍全幅利用**：两种样本下 SOC 区间均为 [1200, 10800]，无"排空/顶格卡死"迹象。
3. 计划层（2 日滚动、末端自由）不受影响；修正仅涉及执行层。

## 5. 落地与影响

- 修正：`q3_proto.simulate_day_rt_hedge` 末段改走 `run_exec(exec_policy, ..., last=True)`；
  `consistency.EXEC_POLICY = "free"` 现全路径生效（Q2/Q4 原本即无目标）。
- **受影响正式结果**：`result3`（1360.3 万）为修复前混合口径（= `dayend`）产物，须按
  `free` 重算；Q3 参数（λ/κ/m）在修正后的执行器下重选（`q3_tune.py`）；`result4-*`
  随统一重算一并更新。
